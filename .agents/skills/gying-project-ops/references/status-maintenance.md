# 状态文档维护

将 `docs/current-project-status.md` 维护为当前运维交接文档，而不是流水账、提交历史或原始日志的替代品。

## 读取准备

1. 定位仓库根目录并确认当前分支、提交和工作树状态。
2. 显式按 UTF-8 完整读取状态文件。
3. 运行 `collect-ops-snapshot.ps1`，区分仓库预期状态与在线观测状态。
4. 用户指定参考分支时，读取该分支的状态文档和相关配置差异，记录参考提交。
5. 编辑前确定本次事实变化会影响哪些章节，保留用户已有无关改动。

Windows PowerShell 5.1 必须使用 `Get-Content -Encoding UTF8`。默认解码可能把有效中文显示为乱码。

## 必需章节

- `当前目标`：项目当前要解决的问题和主要运行链路。
- `运行架构`：入口、核心服务、数据依赖、外部集成和时区。
- `已具备能力`：仅记录代码已具备或目标环境已验证的当前能力，可按领域设三级标题。
- `配置与安全`：敏感值边界、配置来源、数据安全和部署约束。
- `仍需处理`：剩余工作、前置条件和下一步验证。
- `长期不变量`：跨版本仍应成立的数据和架构约束。
- `验收`：保留仍有交接价值的验证结论和可重复执行的验收命令。

`更新时间` 使用 Asia/Shanghai 时区的 ISO 日期 `YYYY-MM-DD`。

## 分支同步

- 以用户指定分支的最新提交为事实基线，不以另一个工作目录的未提交业务改动替代分支证据。
- 先比较状态文档，再检查 Docker、环境变量、数据库迁移、MCP 和 Resource Hub 配置差异。
- 只同步文档和 Skill；除非用户另行要求，不合并或复制业务代码。
- 参考分支描述的是代码能力时写“已具备”；只有真实环境验证后才写“已部署”或“已启用”。
- 当前在线事实与参考分支冲突时，明确记录部署提交和差异，不把两者混写成同一状态。

## 证据标准

每项重要结论至少具备以下证据中的适用部分：

- 环境、入口和部署提交或镜像标识；
- 使用的命令、接口、查询或页面；
- 结果和验证日期；
- 数据维护前后的关键数量；
- 状态改变时的备份或回滚位置。

状态文档不写入原始日志、密钥、完整 SQL 输出或大段调试过程。一次性资源 ID 只在证明仍需交接的数据变更时保留。

## 更新规则

- 当前证据与旧结论冲突时替换旧结论，不并列保留互相矛盾的“当前事实”。
- 明确区分“代码已具备”“配置已写入”“容器已重建”“真实链路已验证”。
- 未完成项保留到证据闭环；完成后从 `仍需处理` 移除，并在必要时更新能力或验收。
- 外部配置只记录路径和键名称，不记录敏感值。
- 明确记录被禁用的调度器、Worker、计划任务和机器人；任务已注册不等于任务已运行。
- 迁移和恢复记录备份时间、目标提交和恢复验证时间。
- 数据清理写清 dry-run、canonical 记录、关联迁移、软删除标记和影响数量。
- GYING 来源身份要区分外部 ID 与本地 canonical 影片 ID，并记录严格匹配条件。
- Resource Hub 修复要区分重跑原转存、重建任务、重新搜索、创建自有分享和正式入库。
- 用户正在编辑同一段内容时合并修改，不覆盖无关内容。

## 运维更新顺序

1. 获取变更前快照。
2. 比较参考分支和当前文档。
3. 执行获准的运维操作。
4. 验证用户可见路径、日志、数据和外部副作用。
5. 获取变更后快照。
6. 只修改受影响章节。
7. 重新完整读取 UTF-8 文件，排查矛盾、过期和敏感信息。
8. 检查 diff，确认没有业务代码和无关改动。

## 时效检查

每次重要维护都要检查：

- 当前部署目录、分支、提交和镜像；
- `backend`、`frontend`、`gying-source`、`social-publisher`、`nginx` 及依赖容器状态；
- 对外端口、nginx 入口和前端服务端渲染；
- MySQL 版本、表集合、`movie_source_identity`、时区、备份和架构漂移；
- `.env.example` 与在线配置键是否一致；
- GYING 当前账号状态、共享 Session、PoW 和内部 token；
- Resource Hub 主开关、Worker、PanSou/Panso、quark-auto-save 和自有分享；
- OpenClaw、NapCat、原 QQ 频道桥接、多平台发布账号、凭据卷、微博会话和计划任务；
- 未解决事故、迁移任务和长期不变量。

纯格式调整不更新时间；只有复核或改变了运维事实时才更新时间。
