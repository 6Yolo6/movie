## 三个独立周榜

来源严格为 GYING `/hits/mv/week`、`/hits/tv/week`、`/hits/ac/week`，分别对应电影、剧集、动漫。缺失榜单、错误类型或非 week 数据失败关闭，不回退到综合/全时热门。

在「影视资源中心 → 采集设置 → 本周热门 · 独立网盘工作流」分别配置：

- 启用开关，默认启用。
- 间隔天数，默认 7，范围 1–365。
- 每轮前 N 部，默认 5，范围 1–20；这是影片数限制，不是网盘字节上限。
- 显示下次时间、上次时间和执行状态。

首次初始化以及修改频率/开关后等待一个完整间隔，不在上线或保存设置时立即大批转存。只修改 N 不改变原定下次时间。受 Resource Hub 主开关和 Worker 开关共同控制。

优先复用已有分享；不为补齐夸克和迅雷两种 provider 重复保存影片。周榜夸克转存使用一次性即时执行，不向 quark-auto-save 注册新的每日追更任务；即时执行未启用时失败关闭。夸克周榜失败不会自动排队 PanSou fallback。

计划在网络副作用发生前持久化下一次执行时间；失败/重启不会每分钟重放。每次扫描最多领取一个到期榜单，另外的到期榜单在随后扫描执行。该锁适用于当前单 backend 实例；多实例需要另行引入数据库租约。进程中断时可能保留 RUNNING 审计状态，但下次时间仍是完整间隔后，不自动重放旧任务。

## 接口与持久化

现有管理员配置 GET/PUT 增加 `weeklyTransferSchedules`，必须完整包含 mv/tv/ac 三项：

```json
[
  {"typeCode":"mv","enabled":true,"intervalDays":7,"maxItems":5},
  {"typeCode":"tv","enabled":true,"intervalDays":7,"maxItems":5},
  {"typeCode":"ac","enabled":true,"intervalDays":7,"maxItems":5}
]
```

服务器忽略客户端提供的运行时间、状态和任务 ID，防止篡改为立即执行。计划存于现有 sys_config 的 `resource.hub.gying.weekly_transfer_schedules`，采用版本化紧凑 JSON 以适配 VARCHAR(500)，读取时兼容早期描述式 JSON，对外 API 仍为上述完整字段；不需要建表迁移。审计任务类型 `WEEKLY_TRANSFER`、来源 `GYING_WEEKLY`，普通 Worker 不消费此类型。source 新增需现有内部 token 的 GET `/weekly-popular?typeCode=mv&limit=5`。

## 迅雷保存路径修复（2026-10-05，代码已部署）

当前配置目标为“我的转存 / 影视剧资源分享(先转存后再查看) / GYing Resource Hub / 影片 / 原分享子目录”；“我的转存”下另一个同级 GYing Resource Hub 是空的旧目录，不是现用目标。

旧流程先创建目标目录，调用分享转存，再把返回的文件 ID 搬入目标。两个不充分的判定会漏搬/误报完成：目录里已有任意视频就跳过搬移；搬移 API 返回成功后只验证存在视频，不确认本轮所有文件实际到位。目录查找原先只读前 100 项，单组搬移恢复信息还可能丢失季目录目标。

本次修复：

- 完整分页查找系统目录与各级目标目录，不因已有目录落在后页而重复建目录。
- 复用必须覆盖该组全部预期视频名；已有部分或不同视频集时失败关闭，不盲目再转存。
- 每轮返回的文件 ID 都逐一确认位置；仅对尚未在目标的文件搬移，并轮询到全部到位。已有旧视频不能跳过这一步。
- 原目标、季目录、任务返回及每组文件 ID 持久化到现有 response_payload；搬移、落盘核验或分享失败后保留 WAITING_SHARE，新进程复用已提交计划，不重新转存。
- 分享前逐组核对全部预期视频；无文件 ID 时只精确匹配预期文件名和转存时间，不再用前缀模糊选根目录文件。

此修复不自动处理历史 SUCCEEDED 或归属不明文件，不承诺远端转存请求与本地持久化之间具备分布式事务；首次提交中断/部分远端请求结果不明仍须人工核对，不能直接重放。
