# 多平台发布运维

完整契约统一维护在[多平台发布与重试运维](../../../../docs/social-publishing.md)，接口清单见[API](../../../../docs/api.md#多平台发布)。涉及重试、账号、会话、部署或恢复时先读上述文档，不使用旧的三状态模型。

## 决策要点

- backend QQBot/每日推荐、宿主机原频道 CLI/桥接、独立 `social-publisher` 是三条链路；凭据、目标和计划任务不能混用。NapCat 不恢复。
- 只有 PENDING/PREPARE_FAILED 且目标存在/启用时可普通重试。管理 retry 对 POSTED 也返回 409；内部 publisher 才会复用 POSTED 结果。
- PREPARING/PUBLISHING/UNKNOWN/历史 FAILED/未识别状态不自动重放。超时、HTTP 错误或进程重启不能证明未发出；HTTP 200 也可能是 `ok:false`。
- 认领与发送保护按日志 ID，不是同影片跨资源版本的全局 exactly-once；不要新建另一条任务绕过阻断。
- 原子状态由 publisher 管理，不能用 SQL 批量改回 PENDING，也没有自动租约释放。先只读核对外部结果，再审查单条恢复。
- 只检查凭据键名、受保护来源和就绪结果。QQ/微博两个状态卷、发布表和实际运行参数都在恢复范围；健康信息不能替代真实成功帖子。
- 删除 QQ 账号会删除其凭据目录并停用目标；不是无害清理。
- 变更状态机时 backend/publisher 及前端策略协调切换，不能只 rebuild publisher。会话更新也走[最小部署](../../../../docs/deployment.md)，不默认发送验证帖子。
- 已获批的真实测试必须指定账号、目标和计划保留内容；未获批时只做只读/mocked 验证，真实发帖留作待验收。

## 排查顺序

1. 核对当前提交、实际镜像、调度与目标开关，勿用迁移默认值推断生产状态。
2. 只读检查内部 token 一致性、账号目录/权限、会话 readiness 与日志状态。
3. 先区分发送前失败、在途和未知结果，再决定能否进入普通重试；认证/验证码问题先停止盲重试。
4. 需要暂停调度或变更凭据时说明范围、备份、复核和恢复方案；不改无关目标。
5. 记录执行窗口、外部结果核对及未验证范围；手机 mock 回归不等于真实账号发帖验收。
