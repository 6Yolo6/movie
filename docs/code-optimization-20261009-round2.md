## 1. 种子响应：在认证探测前执行限额

- 原先虽以 streaming 发起请求，但登录/PoW 探测会访问 Response.text/json，可能先读完整个响应，最终 2 MiB 检查已经太晚。
- 新增可选 max_response_bytes。使用限额时强制 stream=True；先拒绝超限的 Content-Length，再独立累计解码后的流字节，不能依赖缺失、伪造或错误的长度头。
- 原始 GET、PoW 后的 GET、登录后的 GET 均经过同一有界读取。缓存完成后，text/json/content 复用 requests 的正常内容缓存；fetch_torrent_file 不再额外创建第二个 bytearray。
- 替换响应及异常路径关闭连接；普通无上限调用保持原契约。会话锁、访问间隔、认证顺序、HTTPS 主机白名单、禁止跳转及原始 info 字节 BTIH 校验不变。
- **2 MiB 是响应正文上限，不是进程 RSS 上限**；认证解析仍可能创建有界的文本对象。未提高上游采集频率。

## 2. 发布：持久化认领与不确定结果保护

### 状态规则

| 状态 | 含义 | 自动／手动普通重试 |
| --- | --- | --- |
| PENDING | 尚未认领 | 允许，目标须启用 |
| PREPARE_FAILED | 已确认在发送边界之前失败 | 允许，目标须启用 |
| PREPARING | 已认领，准备中 | 拒绝 |
| PUBLISHING | 已持久化即将发送的状态 | 拒绝 |
| UNKNOWN | 发送或回执／持久化结果不确定 | 拒绝，须核验外部平台 |
| POSTED | 已确认并记录成功 | 不重发，返回保存结果 |
| 历史 FAILED、未知状态 | 不能证明未曾发送 | 拒绝，须人工核验 |

- publisher 用一条条件 UPDATE 原子认领同一日志 ID，不跨外部请求持有数据库事务，也没有会自动释放的租约或超时重置。
- QQ 与微博发送前必须等待 beforeSend：先把状态写成 PUBLISHING，再进行不可逆出站。边界写入确认丢失也按不确定情况保护，不冒险补发。
- 边界前错误记 PREPARE_FAILED；边界后错误记 UNKNOWN。已提交 POSTED 但写入回执丢失时，不降级已成功记录。
- 如果 UNKNOWN 写入也失败，PREPARING/PUBLISHING 留在库中继续阻止重放；数据库读取也失败时返回不可自动重试的未确认结果。
- QQ 内容文件采用 UUID、独占创建、0600 权限；已确认发送后的临时文件清理失败不再把成功变成可重试失败。
- backend 不再把历史行重置成 PENDING；插入唯一键竞争只重读胜出行。候选查询排除同目标／同影片已有受保护状态，重试接口对不安全状态返回 409。
- 发布概览把逐状态 COUNT 合并为一次分组读取，保留大小写比较兼容；展示准备中／发送中、结果待核对。既有监控失败计数也纳入 PREPARE_FAILED，但不把 UNKNOWN 伪称为已失败。
- 前端不再把 HTTP 200 等同于已发帖；使用信息提示，并在 HTTP 错误后同样刷新日志和概览。

### 保证边界

这是**每个日志 ID 的持久化发送保护**，不是所有资源版本、影片和外部平台的全局 exactly-once。不同资源版本的并发建单仍不等于拥有“目标＋影片”全局唯一约束。进程崩溃后的 PREPARING/PUBLISHING 也不会自行解锁，需要先核查实际副作用。没有提供“强制重试 UNKNOWN”的快捷入口。

## 3. 手机端与首屏一致性

- 发布目标与发布日志在小于 768px 时改为纵向卡片，不把 1900px 宽桌面表格简单缩小；桌面保留表格。
- 手机目标卡片可展开编辑名称、QQ 频道／版块、启用开关、时间、篇数、间隔及模板，保留保存、发布和确认删除；编辑草稿放在页面层，手机／桌面切换不丢输入。
- 日志卡片完整展示状态、目标、影片／资源、错误和时间。长中文、连续英文及错误文本可换行，手机不依赖 hover 才能知道禁止重试的原因。
- 主要卡片操作和重试按钮至少 44px 高；筛选独占一行，卡片标题与账号操作可换行，历史支持手机分页。
- 手机和桌面共用同一个重试按钮及状态规则，停用／已删除目标与受保护状态均禁止操作。
- 修复既有 i18n 初始化根据浏览器偏好直接改变首屏，导致服务端英文与客户端中文不一致的问题：初始快照统一英文，挂载后恢复保存语言或浏览器语言；localStorage 被禁用时可回退，不覆盖已有偏好。
- 验收是 Headless Edge 的响应式视口模拟，不等同于 iOS Safari 或 Android 真机验收，也不是全站每个管理页面的重新设计。

## 5. 部署前检查、发布与回退约束

- 2026-10-10 仓库运维就绪检查为 10 PASS / 2 WARN / 0 FAIL。两条警告仍为既有迁移文档漂移和新库架构覆盖；这个检查**不等于生产安全门禁通过**。
- 核对的 docs/security/hardening-gates.md 最新既有台账为 2026-10-08，G01–G11 全部未关闭；本轮未将历史结果标注为今天重新扫描的结果。Access、分服务身份／policy、恢复验收也没有新的通过证据。
- 本轮没有结构迁移：已有 status VARCHAR(30) 可容纳新状态；仅更新建表文件中的中文状态注释，**没有执行 schema.sql 或增量 SQL**。
- 门禁通过后的受影响服务为 backend、social-publisher、gying-source、frontend；必须使用实际生产项目和覆盖配置，不能直接拿目标 Compose 批量替换现役服务。
- backend 与 publisher 必须在暂停相关调度、限制管理发布入口并排空／核对在途任务的维护窗口协同切换。旧 backend 会重置状态，旧 publisher 不执行认领，不能混合新旧写入方。
- 回退同样需要先隔离发布入口并核对在途记录；不能仅回退某个发布组件，更不能为兼容旧版而把 UNKNOWN/PUBLISHING/历史 FAILED 批量改回 PENDING。优先保留安全状态机作前向修复。
- 实际部署前仍需保存现役镜像、外部配置、发布表及凭据卷的可恢复备份；本轮未生成或声称完成生产恢复检查点。

## 后续明确保留项

- UNKNOWN／崩溃在途任务的人工核验与受控恢复流程；跨资源版本同片并发唯一性需独立设计并评估历史数据。
- 海报 preparePoster 的 arrayBuffer 在 15 MiB 判断前读取完整响应，仍是下一批候选，本轮没有顺带重写。
- iOS Safari／Android 实机、真实账号管理操作和外部平台发布链路仍需独立授权与验收；不能用 mock 保存、视口截图和 MySQL 合成记录替代。
